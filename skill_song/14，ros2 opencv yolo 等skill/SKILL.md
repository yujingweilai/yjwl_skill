# ROS 2 机械臂开发与视觉抓取

## 适用范围

当用户需要在 Ubuntu 22.04 上开发、仿真、调试或部署机械臂应用时，使用本 Skill。覆盖以下内容：

- ROS 2 节点、话题、服务、动作、参数与 launch 文件。
- RViz2 中的机器人模型、TF、轨迹、点云、标记与交互式目标位姿可视化。
- MoveIt 2 的运动学、规划组、碰撞场景、路径规划、末端执行器与抓取流程。
- Gazebo 中的 URDF/Xacro、ros2_control、传感器、物理仿真与机械臂联合调试。
- Python（rclpy）控制节点、相机订阅、坐标变换与任务编排。
- OpenCV 图像处理、相机标定、目标检测、深度图与位姿估计。
- YOLO 目标检测、三维定位、坐标转换与视觉抓取。

## 不适用范围

- 与机器人、机器视觉或 ROS 2 无关的通用软件问题。
- 未经用户确认，直接控制真实机械臂执行大范围或高速运动。
- 绕过急停、限位、碰撞检测或厂商安全机制。

## 基本原则

1. **先确认环境与目标**：明确 ROS 2 发行版、操作系统、机械臂型号、仿真或真机、相机类型、夹爪类型、控制器接口及目标任务。
2. **先分析事实再给结论**：用户提供代码、日志、URDF、Xacro、配置或终端输出时，先阅读实际内容，不猜测不存在的接口、话题和参数。
3. **分层定位问题**：依次检查系统依赖、机器人描述、TF 树、控制器、传感器数据、规划场景和应用逻辑。
4. **安全优先**：真机默认使用低速、小范围运动；先在 RViz2 或 Gazebo 验证，再连接实机。
5. **坐标变换可追溯**：明确 `world`、`map`、`base_link`、`tool0` 和相机光学坐标系，并通过 TF2 验证父子关系、变换方向与时间戳。
6. **先最小可运行，再逐步扩展**：优先提供可独立验证的最小节点、启动命令和检查步骤，再增加感知、抓取和任务状态机。
7. **保持最小改动**：修改已有项目时遵循原有框架，优先复用已有函数和配置，不引入无关依赖或不必要抽象。

## 标准工作流

### 1. 收集必要信息

优先确认：

- Ubuntu 与 ROS 2 发行版，例如 Ubuntu 22.04 + ROS 2 Humble。
- 机械臂型号、自由度、末端工具、控制方式及厂商驱动。
- 目标任务：关节运动、末端位姿运动、避障、抓取、视觉伺服或标定。
- 运行环境：Gazebo、RViz2、真实硬件，或三者组合。
- 传感器类型：RGB、RGB-D、双目或激光雷达，以及相机安装方式。
- 是否已有 URDF/Xacro、MoveIt 配置包、控制器配置和 ROS 2 工作空间。
- 已知的错误日志、复现步骤、预期现象和实际现象。

信息不足但不妨碍推进时，应明确列出合理假设；关键信息会影响安全或方案选择时，应先向用户确认。不得虚构机械臂接口、话题名称、标定参数或硬件能力。

### 2. 建立并验证 ROS 2 基础链路

按以下顺序处理，每一步验证通过后再进入下一步：

1. 创建或检查工作空间与目标包。
2. 启动 `robot_state_publisher`，确认 URDF/Xacro 能正确展开。
3. 使用 `joint_state_publisher_gui` 或控制器发布关节状态。
4. 在 RViz2 中确认机器人模型可见，TF 树完整且无断链。
5. 接入 ros2_control 控制器，验证关节命令和状态反馈。
6. 启动 MoveIt 2，检查规划组、末端执行器、碰撞模型和规划结果。
7. 最后接入相机、OpenCV、YOLO、抓取策略和任务状态机。

### 3. RViz2 排查

依次检查：

- `Fixed Frame` 是否为存在且稳定的全局坐标系，例如 `world` 或 `base_link`。
- `robot_description` 是否已加载，`RobotModel` 是否可见。
- `/joint_states` 是否持续发布，关节名称是否与 URDF 一致。
- `/tf` 和 `/tf_static` 是否包含从 `base_link` 到工具及相机的完整链路。
- MotionPlanning 插件中的 Planning Group、Goal State 和 Planning Scene 是否正确。
- 轨迹、Marker、PointCloud2 和图像话题的消息类型、时间戳与 QoS 是否匹配。

优先使用以下命令获取事实：

```bash
ros2 node list
ros2 topic list
ros2 topic info /joint_states --verbose
ros2 topic echo /joint_states --once
ros2 run tf2_tools view_frames
ros2 run tf2_ros tf2_echo base_link tool0
```

应根据用户项目替换示例中的话题和坐标系名称，不得把示例名称当成项目事实。

### 4. MoveIt 2 开发与排查

- 明确规划组、末端链、参考坐标系和目标形式：关节角、末端位姿或路径约束。
- 先在 RViz2 验证规划成功率和碰撞情况，再连接控制器执行。
- 规划失败时检查目标可达性、起始状态、碰撞物体、关节限制、姿态约束和规划时间。
- 抓取任务拆分为：预抓取、接近、闭合夹爪、抬升、移动、放置、松开和撤离。
- Python 接口必须与当前 ROS 2/MoveIt 2 版本匹配；接口受限时，再考虑动作、服务或 C++ 节点。
- 规划成功不等于执行安全，真机执行前必须检查速度、加速度、限位和碰撞环境。

### 5. Gazebo 与 ros2_control

同时检查模型、传动和控制三层：

- 使用 Xacro 参数化机械臂、夹爪、传感器和材料属性。
- 为每个可控关节配置正确的传动、限制和 ros2_control 硬件接口。
- 保证控制器、URDF 和 MoveIt 配置中的关节名称完全一致。
- 检查重力、惯量、碰撞体和关节阻尼，避免模型抖动、下坠或穿模。
- 将仿真与真机控制器的接口差异放在配置层，尽量不改上层任务逻辑。
- Gazebo 视觉效果不能直接代表真机效果；真机部署前必须重新验证标定、光照、延迟和安全边界。

### 6. OpenCV 与 YOLO 视觉抓取

按“检测 → 定位 → 转换 → 验证 → 执行”组织流程：

1. 获取并校验图像、相机内参、畸变参数、分辨率和时间戳。
2. 使用 YOLO 输出类别、置信度和边界框，并明确模型版本、输入尺寸、类别和阈值。
3. 使用深度图、双目、已知平面或姿态估计方法，将像素点转换为相机三维坐标。
4. 使用手眼标定结果和 TF2，将目标从相机坐标系转换到 `base_link` 或规划坐标系。
5. 根据目标尺寸、朝向和夹爪能力生成抓取候选位姿。
6. 使用 MoveIt 2 验证可达性、碰撞和路径。
7. 执行前重新确认目标仍有效，执行后通过视觉或夹爪反馈确认抓取结果。

仅有单目 RGB 图像时，不能直接把二维检测框中心当作可靠的三维抓取点。必须明确深度来源、平面假设或姿态估计方法，并说明误差来源。

### 7. Python（rclpy）节点规范

- 将节点职责限制为感知、坐标转换、规划请求或执行监控中的一个或少数几个职责。
- 使用 ROS 2 参数管理话题名、坐标系、阈值、模型路径和运行模式。
- 为图像和点云选择匹配的 QoS，并关注丢帧、延迟和时间同步。
- 对 TF 查询、动作结果、控制器状态和模型加载失败进行明确处理。
- 不在订阅回调中执行长时间阻塞操作；复杂流程使用状态机、定时器或动作接口。
- 修改或新增函数时，添加中文注释，说明函数名称、参数、返回值和用途。
- 运行日志使用清晰的英文信息，至少能定位节点、阶段和失败原因。
- 不使用 `goto`，不引入未定义的变量、函数、话题或参数。

## 常见故障诊断

| 现象 | 优先检查 | 常见修复方向 |
| --- | --- | --- |
| RViz2 无机器人模型 | `robot_description`、URDF 解析、Fixed Frame | 修复模型加载、坐标系和网格路径 |
| 机器人姿态不动 | `/joint_states`、关节名称、控制器状态 | 对齐关节名称并检查状态发布 |
| TF 外推报错或断链 | 时间戳、静态变换、父子坐标关系 | 修正发布时间、变换方向和 TF 链路 |
| MoveIt 2 规划失败 | 可达性、碰撞、关节限制、目标姿态 | 调整目标、约束或规划参数 |
| Gazebo 抖动或下坠 | 惯量、碰撞体、阻尼、控制器增益 | 修正动力学参数与控制器配置 |
| YOLO 检测漂移 | 图像同步、预处理、输入尺寸、阈值 | 校验相机数据和推理配置 |
| 抓取位置偏移 | 内参、深度、手眼标定、TF | 重新标定并验证变换方向 |
| 真机执行异常 | 控制模式、限位、速度、状态反馈 | 立即停止，降速后在安全空间逐层验证 |

## 代码修改流程

用户要求修改项目时，按以下步骤执行：

1. 读取相关代码、配置、日志和项目结构。
2. 说明已确认的事实、问题位置和必要假设。
3. 采用最小改动，保持原有程序框架并复用已有函数。
4. 确保函数中文注释完整，新增日志使用英文。
5. 执行与改动直接相关的语法检查、构建或测试。
6. 复核符号、依赖、话题、参数、坐标系和接口，确认未引入未知变量或函数。
7. 用大白话总结改了什么、为什么改、如何验证及仍需注意的风险。

## 输出要求

回答或实现时，根据任务提供必要内容：

- 当前判断所依据的事实与明确假设。
- 推荐的包结构、关键配置职责和启动顺序。
- 可直接运行的最小示例，并注明依赖、命令和预期现象。
- 坐标系、消息类型、话题、服务、动作和参数约定。
- 可执行的验证步骤与故障排查命令。
- 仿真与真机的差异、风险和上线前检查项。
- 修改后的复核结果，不声称未实际执行的测试已经通过。

输出应聚焦用户当前问题，不扩展无关功能。若用户已提供代码、日志、URDF、Xacro、MoveIt 配置或终端输出，必须先基于实际内容分析，再给出精确修改建议。
