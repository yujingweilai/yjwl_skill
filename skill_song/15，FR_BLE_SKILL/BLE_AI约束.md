# 嵌入式 C 开发规范

本 skill 用于指导通用嵌入式 C 固件项目的开发、修改、优化与审查，确保代码质量、框架一致性和可维护性。

## 核心原则

### 1. 保持原有框架结构

**未经用户明确同意，禁止改变项目既有的分层、模块边界、任务/调度机制、状态机框架、驱动接口和业务调用关系。**

新增或修改的代码必须符合现有项目的组织方式、命名风格和调用流程。若确实需要调整框架结构，必须：

1. 先询问用户是否同意。
2. 用大白话说明必须调整的原因。
3. 对比原方案与新方案的优缺点及影响范围。
4. 获得用户明确批准后才能实施。

### 2. 用户自定义状态机框架规范

项目中直接创建或维护的状态机应遵循以下规范；若项目已有状态机定义，应优先沿用现有结构，禁止无必要重构。

#### 2.1 状态机结构定义

```c
/* 状态机结构体，放在 .h 文件中 */
typedef struct {
    uint8_t current_state;    // 当前状态
    uint8_t previous_state;   // 上一个状态
    uint8_t event;            // 触发事件
    bool state_changed;       // 状态是否改变标志
} StateMachine_t;
```

#### 2.2 状态枚举定义

```c
/* 状态枚举，放在 .h 文件中 */
typedef enum {
    STATE_IDLE = 0,      // 空闲状态
    STATE_RUNNING,       // 运行状态
    STATE_ERROR,         // 错误状态
    STATE_MAX            // 状态最大值，用于边界检查
} State_t;
```

#### 2.3 事件枚举定义

```c
/* 事件枚举，放在 .h 文件中 */
typedef enum {
    EVENT_NONE = 0,      // 无事件
    EVENT_START,         // 启动事件
    EVENT_STOP,          // 停止事件
    EVENT_RESET,         // 复位事件
    EVENT_MAX            // 事件最大值，用于边界检查
} Event_t;
```

#### 2.4 状态机处理函数

```c
/**
 * @brief 处理状态机事件并完成状态转换
 * @param sm 状态机结构体指针
 * @return 0：处理成功；其他值：错误码
 * @note 应由项目现有的周期处理机制或事件处理流程调用
 */
int state_machine_process(StateMachine_t *sm)
{
    if (sm == NULL) {
        return -1;  // 参数错误
    }

    sm->state_changed = false;

    switch (sm->current_state) {
        case STATE_IDLE:
            // 空闲状态处理
            if (sm->event == EVENT_START) {
                sm->previous_state = sm->current_state;
                sm->current_state = STATE_RUNNING;
                sm->state_changed = true;
            }
            break;

        case STATE_RUNNING:
            // 运行状态处理
            if (sm->event == EVENT_STOP || sm->event == EVENT_RESET) {
                sm->previous_state = sm->current_state;
                sm->current_state = STATE_IDLE;
                sm->state_changed = true;
            }
            break;

        case STATE_ERROR:
            // 错误状态处理
            if (sm->event == EVENT_RESET) {
                sm->previous_state = sm->current_state;
                sm->current_state = STATE_IDLE;
                sm->state_changed = true;
            }
            break;

        default:
            // 未知状态，恢复到空闲状态
            sm->previous_state = sm->current_state;
            sm->current_state = STATE_IDLE;
            sm->state_changed = true;
            break;
    }

    sm->event = EVENT_NONE;  // 事件处理完成后清除事件标志

    return 0;
}
```

#### 2.5 状态机框架约束

- **优先复用既有框架**：项目已有状态机时，状态结构、枚举定义和事件传递方式必须保持一致。
- **状态转换必须清晰**：每次状态切换都要有明确事件或条件触发。
- **状态处理必须完整**：每个有效状态都应在 `switch-case` 中处理。
- **必须有默认处理**：`switch` 语句必须包含 `default` 分支。
- **状态机必须初始化**：系统启动或模块初始化时，状态机成员必须被明确赋初值。
- **事件必须清除**：事件处理结束后应清除事件标志，避免重复触发。
- **文件组织必须正确**：宏、结构体、枚举、函数声明放在对应 `.h` 文件；实现放在 `.c` 文件。

#### 2.6 状态机使用示例

```c
// 全局状态机变量，放在 .c 文件中
StateMachine_t g_motor_sm;

/**
 * @brief 初始化电机状态机
 * @param 无
 * @return 无
 * @note 应在模块启动时调用一次
 */
void motor_state_machine_init(void)
{
    g_motor_sm.current_state = STATE_IDLE;
    g_motor_sm.previous_state = STATE_IDLE;
    g_motor_sm.event = EVENT_NONE;
    g_motor_sm.state_changed = false;
}

/**
 * @brief 向电机状态机发送事件
 * @param event 需要处理的事件类型
 * @return 无
 */
void motor_send_event(Event_t event)
{
    g_motor_sm.event = event;
}

/**
 * @brief 周期处理电机状态机及状态切换后的动作
 * @param 无
 * @return 无
 * @note 由项目现有的主循环、定时调度或任务机制周期调用
 */
void motor_state_machine_update(void)
{
    (void)state_machine_process(&g_motor_sm);

    if (!g_motor_sm.state_changed) {
        return;
    }

    switch (g_motor_sm.current_state) {
        case STATE_RUNNING:
            // 启动电机
            break;

        case STATE_IDLE:
            // 停止电机
            break;

        default:
            break;
    }
}
```

### 3. 禁止幽灵变量

- 所有声明的变量、函数、宏和类型必须被实际使用。
- 所有被使用的变量、函数、宏和类型必须有明确且可追溯的定义。
- 禁止引入未定义、未初始化或未使用的内容。
- 新增局部变量前，先检查能否复用现有变量或参数。

### 4. 中文注释与日志要求

新增或修改的代码元素必须提供清晰的中文说明；函数注释需说明函数名称、作用、参数、返回值和注意事项。项目已有日志机制时，应优先复用，并使用英文日志内容。

**函数注释示例：**

```c
/**
 * @brief 读取传感器采样值并更新缓存
 * @param channel 传感器通道编号
 * @param value 用于保存采样结果的输出地址
 * @return 0：读取成功；其他值：读取失败
 * @note 调用前应确保硬件接口已完成初始化
 */
```

**变量注释示例：**

```c
int sample_count = 0;  // 采样计数器，用于记录当前采样次数
```

**宏定义注释示例：**

```c
#define MAX_BUFFER_SIZE 1024  // 最大缓冲区大小，单位：字节
```

**英文日志示例：**

```c
LOG_INFO("Sensor initialized successfully");
LOG_ERROR("Sensor read failed, channel=%u", channel);
```

### 5. 代码风格规范

#### 5.1 禁止 `goto` 语句

- 使用结构化控制流，如 `if-else`、`switch-case` 和循环。
- 通过函数封装、返回值和早返回处理复杂逻辑。

#### 5.2 减少嵌套层数

- 嵌套深度尽量控制在 3～6 层以内。
- 优先使用早返回（early return）模式。
- 能使用分支判断处理的逻辑，不使用不必要的深层嵌套。

**错误示例：**

```c
if (condition1) {
    if (condition2) {
        if (condition3) {
            // 深层嵌套
        }
    }
}
```

**正确示例：**

```c
if (!condition1) return;
if (!condition2) return;
if (!condition3) return;
// 扁平化逻辑
```

#### 5.3 文件组织规范

**`.c` 文件内容：**

- 函数实现。
- 静态变量（文件作用域变量）。
- 局部变量定义。

**`.h` 文件内容：**

- 宏定义（`#define`）。
- 函数声明。
- 类型定义（`typedef`、`struct`、`enum`）。
- 配置常量。
- 头文件保护符（`#ifndef`、`#define`、`#endif`）。

### 6. 最小改动原则

#### 6.1 优先复用现有资源

- 优先使用已有变量、宏、类型和配置。
- 优先调用已有函数和接口。
- 优先在原函数内完成修改，避免无必要新建函数。
- 避免过度封装、不必要抽象和无关重构。

#### 6.2 改动评估标准

修改前必须评估：

1. 是否确实需要改动？
2. 能否基于现有代码完成？
3. 改动范围是否已经最小化？
4. 是否引入了不必要的复杂性、变量、函数或依赖？

### 7. 分析与复核流程

#### 7.1 修改前分析

用大白话说明：

- 当前代码或需求要解决什么问题。
- 为什么采用该修改方式。
- 修改后的预期效果。

#### 7.2 修改后复核

至少检查以下内容：

- 是否保持原有程序框架和调用关系。
- 是否存在编译错误、逻辑错误或异常风险。
- 新增或修改的变量、函数、宏是否已正确定义、初始化和使用。
- 函数声明、参数、返回值和调用关系是否匹配。
- 内存、缓冲区、资源释放和并发访问是否合理。
- 中断、定时器、调度机制和模块时序是否受到非预期影响。
- 是否复用了现有资源，且未引入未知变量或函数。

#### 7.3 修改总结报告

修改完成后，必须用大白话说明：

1. **改了哪个文件**：列出所有修改的文件路径。
2. **为什么这样改**：说明每个文件的修改原因。
3. **改动位置**：具体到函数名和行号范围。
4. **影响范围**：说明可能影响的模块、接口或行为。
5. **复核结果**：说明已检查的项目及是否发现问题。

**报告示例：**

```text
修改总结：
1. 文件：src/device/sensor.c
   原因：修复传感器读取失败后仍使用旧数据的问题。
   位置：sensor_read_value 函数，第45～60行。
   改动：读取失败时直接返回错误码，不再更新缓存。

2. 文件：include/device_config.h
   原因：调整采样缓冲区大小以适配新的采样长度。
   位置：第23行，SAMPLE_BUFFER_SIZE 宏定义。
   改动：将缓冲区大小从512改为1024。

影响范围：仅影响传感器采样模块及其调用方。
复核结果：未新增未使用变量或函数，原有接口与调用关系保持不变。
```

### 8. 提示词优化与确认机制

#### 8.1 自动优化提示词格式（父类—子类—子类结构）

收到用户需求后，先将其整理为层级结构，确保需求清晰、有条理。

**优化规则：**

- **第一层（父类）**：识别最终目标或大方向，例如“修复通信问题”“优化数据采集”。
- **第二层（子类）**：拆解为具体模块或步骤，例如“接收处理模块”“发送处理模块”。
- **第三层（子类）**：细化具体操作点，例如“校验接收长度”“调整重试条件”。

**优化输出格式示例：**

```text
提示词优化结果：
├── 父类：修复通信异常
│   ├── 子类：接收处理模块
│   │   ├── 子类：校验接收数据长度
│   │   └── 子类：补充接收失败英文日志
│   └── 子类：发送处理模块
│       └── 子类：修正发送完成状态判断
```

**处理方式：**

1. 收到用户需求后，自动分析并整理为层级结构。
2. 将优化后的结构展示给用户，确认理解是否正确。
3. 用户确认无误后，再进入后续开发流程。

#### 8.2 提示词错误检测与确认机制

分析用户需求时，如发现以下问题，必须暂停并用大白话说明，等待用户确认后再继续。

**需要确认的情况：**

- **错别字**：例如“波特律”可能是“波特率”。
- **意思不清楚**：例如“改一下那个东西”未说明具体模块或功能。
- **专业术语可能有误**：例如“DMA中端”可能是“DMA中断”。
- **逻辑矛盾**：例如要求不改框架但同时要求重写整个模块。
- **信息缺失**：例如缺少文件路径、功能描述、目标参数或复现条件。

**确认流程：**

1. 发现问题后立即暂停，不继续实施。
2. 用大白话说明不明确或可能错误的地方。
3. 给出合理猜测或建议。
4. 等待用户确认或补充信息。
5. 补充后仍有疑问时，继续确认直到需求明确。

**确认示例：**

```text
提示词确认：
你提到要修改“串口的波特律”，我猜你想说的是“串口的波特率”？
另外“改快一点”是要提高到多少？请提供目标数值后我再继续。
```

## 工作流程

当用户请求修改、优化或审查嵌入式 C 代码时，按以下步骤执行：

1. **提示词优化**：将用户需求整理为“父类—子类—子类”结构，并展示确认。
2. **提示词检查**：检查错别字、歧义、矛盾和信息缺失；存在问题时先确认。
3. **理解需求**：明确要解决的问题和目标效果。
4. **分析现状**：阅读相关代码，理解原有框架和调用关系。
5. **制定方案**：按最小改动、优先复用原则设计方案。
6. **评估影响**：检查是否涉及框架、接口、时序或资源变化。
7. **征求同意**：如需改变原有框架，先取得用户明确同意。
8. **实施修改**：按照项目风格完成最小必要修改。
9. **补充注释与日志**：为新增或修改内容提供中文注释；按项目机制补充英文日志。
10. **复核检查**：检查变量、函数、调用关系、资源和潜在异常。
11. **输出报告**：用大白话总结修改内容、影响范围和复核结果。

## 蓝牙 / BLE 开发约束

当用户请求新增、修改、优化或审查蓝牙 / BLE 功能时，除遵循本 skill 的通用规范外，还必须遵循以下约束。若用户未明确芯片、协议栈、移动端平台、目标距离、数据量、时延、续航和连接数量，不得臆测实现能力，应先确认关键条件。

### 1. 技术选型与能力边界

- 必须先区分 BLE、经典蓝牙（BR/EDR）和 Mesh，禁止将三者的能力、接口和性能指标混为一谈。
- BLE 适用于低功耗、近距离、小数据量的控制、状态上报和传感器采集；不应承诺其满足持续大数据传输、实时视频或硬实时闭环控制。
- 不得仅依据芯片或蓝牙版本宣传参数承诺距离、吞吐、时延、连接数量或新特性；必须以实际芯片、SDK、协议栈、天线设计及对端设备的实测结果为准。
- 2M PHY、LE Coded PHY、扩展广播、DLE、大 MTU、LE Audio 等均可能是可选能力；使用前必须确认本端、对端和当前 SDK 均支持，协商失败时必须具备兼容处理。
- 手机或网关可拒绝或调整连接间隔、PHY、MTU 等请求，应用层不得假定请求参数必然生效。

### 2. 射频、距离与共存约束

- 蓝牙工作在 2.4 GHz 频段，设计和测试必须考虑 Wi-Fi、其他无线设备、微波炉、USB 3.0 设备及电机等干扰源。
- 不得按空旷视距宣传距离作为实际稳定通信距离；必须在隔墙、人体遮挡、Wi-Fi 密集、多设备并发等真实场景验证。
- 不得仅以单次 RSSI 判断链路质量、距离或身份可信度；应结合丢包率、重连率、延迟和长期稳定性评估。
- 天线、地平面、电池、金属外壳、屏幕、排线和高噪声电源模块会影响射频性能；涉及硬件设计时必须预留天线净空并依据具体模块参考设计复核。

### 3. 性能、可靠性与协议设计约束

- 物理层速率不等于应用实际吞吐；设计时必须考虑协议开销、连接间隔、MTU、DLE、分片、重传、加密、协议栈调度和无线干扰。
- 广播和 Notification 均不提供端到端可靠送达保证，禁止将其作为关键控制命令、可靠告警或重要数据的唯一传输保障。
- 关键控制命令必须设计应用层确认、命令序号、超时、有限次数重试和幂等处理；不得因重传造成重复执行。
- 传感器流或状态上报应包含序号和必要时间信息，便于接收端发现丢包、乱序或数据过期。
- 大数据或 OTA 传输必须采用分块、长度校验、CRC 或 Hash、流控、超时和断点续传；禁止一次性向协议栈队列大量堆积数据。
- BLE 不得作为唯一的安全控制或失效保护手段。涉及电机、门锁、医疗、工业控制等场景时，必须保留本地超时、失联保护、限位、急停或故障安全机制。

### 4. 低功耗与连接参数约束

- 连接间隔、从机延迟、广播间隔、发射功率、PHY、数据发送频率之间存在功耗、时延、吞吐和稳定性取舍；不得同时无条件承诺超低功耗、超远距离、超高吞吐和毫秒级响应。
- 短连接间隔、高频广播、持续 Notification 或大包连续传输会提高平均功耗，优化前必须明确优先目标。
- 多连接、扫描、广播、连接通信、OTA 等会争用射频、内存和协议栈资源；新增并发功能前必须核对芯片 RAM、协议栈配置和 CPU 负载。

### 5. 安全、权限与隐私约束

- 涉及设备控制、敏感数据、OTA、门锁、支付、医疗或工业参数时，禁止默认使用无 MITM 防护的 Just Works 配对；应优先使用 LE Secure Connections，并结合 Numeric Comparison、Passkey 或 OOB 等适当认证方式。
- 每个 GATT 特征值必须按业务风险配置读、写、通知、指示的加密、认证和授权权限；连接成功不等于已获得业务操作权限。
- 高风险命令必须在应用层再次校验授权、参数范围、会话状态和重放风险，禁止仅凭设备名称、MAC 地址、RSSI 或广播内容授权。
- 广播包默认可被附近设备监听，禁止在广播名称、Manufacturer Data 或 Service Data 中放置密钥、密码、用户身份、固定敏感标识或可直接重放的控制命令。
- 面向个人或移动设备时，应优先使用隐私地址机制，并避免在广播载荷中长期暴露稳定唯一标识，降低被跟踪风险。
- 必须关注芯片厂商和协议栈安全公告，升级到已修复已知漏洞的 SDK / 协议栈版本；不得继续使用已知存在重大安全风险的旧实现。

### 6. 断线恢复、OTA 与验证约束

- 必须明确断线、超时、重连、重新配对和绑定信息清除的处理流程，避免旧会话、旧授权或残留数据被错误复用。
- OTA 必须具备固件完整性校验和来源认证；涉及产品安全时应使用签名验证、版本策略和可恢复的升级机制。
- OTA 期间必须评估供电、复位、断线、手机后台切换和升级失败后的恢复路径，避免设备无法再次启动或连接。
- 修改完成后，除通用复核项外，至少验证：配对与权限、断线恢复、关键命令确认、干扰环境链路、功耗目标、最大并发场景及 OTA 异常恢复。

## FR801x BLE 专项约束

当目标工程使用 FR801x 芯片时，除上述通用约束外，还必须执行以下专项检查。修改前应读取相关源码、头文件、Keil 工程、Scatter 文件和调用关系，确认实际工具链、SDK 接口与内存布局；禁止凭经验新增未经确认的外部符号，禁止擅自迁移工具链、替换 SDK 接口或修改协议栈库。

### 1. BLE 初始化与广播顺序

**正确顺序：**

```text
初始化系统参数
→ 完成 BLE 初始化
→ 设置设备名和 GAP 回调
→ 注册全部 GATT 服务
→ 等待 GAP_EVT_ALL_SVC_ADDED
→ 设置广播参数、广播数据和扫描响应
→ 开始广播
```

**禁止做法：**

- 服务尚未全部注册就开始广播。
- 只修改广播长度字段而不核对实际数组长度。
- 混用 Public 地址和静态随机地址规则。
- 断开后不考虑产品状态就无条件重启广播。
- 收到 MTU 更新后不检查应用层实际发送长度。

### 2. GAP / GATT 回调

- 回调中只进行快速状态更新、事件记录和任务投递；传感器访问、LCD 刷屏、音频处理和复杂格式化应放在任务上下文。
- 处理业务前必须校验事件参数、连接索引、MTU、缓冲区和有效载荷长度。
- 禁止在 GAP、GATT 或中断回调中执行阻塞式 I2C、长循环、音频解码、无限日志或大块动态内存申请。
- 禁止保存生命周期不明确的事件参数或消息指针供异步使用。

### 3. 动态内存与对象生命周期

动态内存申请后必须立即检查结果，例如：

```c
context = os_zalloc(sizeof(ADPCMContext));
if (context == NULL) {
    co_printf("[AUDIO] Decoder context allocation failed\r\n");
    return;
}
```

- 申请、使用、停止、异常退出和重复启动路径必须具有清晰的内存所有权。
- 停止音频等业务时，应先停止相关中断和硬件，再释放链表节点、内部缓冲区及解码上下文，并将指针置为 `NULL`。
- 重复停止必须安全，不得重复释放。
- 禁止申请后不判空就解引用、新申请覆盖旧指针、释放非动态内存，或只释放外层上下文而遗漏内部缓冲区。

### 4. 字符串、数组与边界

- 固定缓冲区必须使用项目现有的有界格式化接口，检查返回长度，并确保字符串以 `\0` 结束。
- 枚举值作为数组下标前必须检查范围，未知值应输出 `UNKNOWN`。
- 禁止对固定数组直接使用无界 `sprintf`，禁止将外部数据直接拼接到容量未经核对的小缓冲区。
- 修改 BLE 数据发送逻辑时，必须同时核对 MTU、协议开销、分片长度和底层接口允许的长度。

### 5. Flash 与内存布局

- 修改资源地址前，必须同时核对 `FLASH_MAX_SIZE`、应用代码区、跳转表、Bonding 信息、Remote Service、静态密钥、图片和音频区域。
- 必须检查 Scatter 文件中的 RO、RW、ZI、HEAP 和 RAM code 区域是否重叠，并依据实际 Flash 型号选择配置。
- 禁止把 4 Mbit 误当作 4 MB，禁止覆盖 `BLE_BONDING_INFO_SAVE_ADDR`、静态密钥、跳转表或其他系统保留区。
- Flash 型号、分区、跳转表或 Scatter 地址不明确时，必须暂停修改并请求用户提供依据。

### 6. FR801x 低功耗

- 启用睡眠前必须建立外设清单，明确每个外设在睡眠前的保持或关闭动作，以及唤醒后的恢复动作。
- 睡眠前后钩子应按工程现有要求放入 `ram_code`；不得放在睡眠期间可能无法执行的区域。
- 唤醒后应按实际丢失状态恢复 UART、GPIO 复用、时钟、中断、PMU、I2S、定时器及相关外设。
- 必须验证睡眠和唤醒后的 BLE 广播、连接、音频和传感器行为。
- 禁止只打开睡眠宏就宣称支持低功耗，也不得忽略高频日志和常驻外设造成的功耗。

### 7. Bond 与配对信息

- 正式产品默认保留配对信息，明确安全参数、密钥地址和擦除策略。
- 只有用户明确要求恢复出厂或测试模式时，才允许清除 Bond，并输出说明原因的英文日志。
- 禁止在每次启动时无条件调用 `gap_bond_manager_delete_all()`，也不得把测试擦除逻辑混入正式启动路径。

### 8. FR801x 暂停修改条件

出现以下情况时，不得猜测实现或扩大改动范围：

- SDK 接口声明、结构体布局或事件参数生命周期不清楚。
- Flash 型号、分区、跳转表或 Scatter 地址不清楚。
- 需要将 ARMCC / Keil 工程迁移到 GCC，但用户没有明确要求。
- 需要修改协议栈库、启动文件、链接脚本或芯片补丁，但缺少对应依据。
- 低功耗唤醒后的外设状态无法确认。
- 内存所有权、缓冲区大小或异步消息生命周期无法确认。

### 9. FR801x 修改后专项复核

- [ ] 已确认并保持原有 ARMCC、Keil 或实际工程工具链。
- [ ] BLE 服务注册完成后才启动广播。
- [ ] GAP / GATT 回调未新增阻塞或耗时操作。
- [ ] 动态内存申请、异常退出、停止和释放路径可追踪且成对。
- [ ] 固定数组、字符串、MTU、事件参数和连接索引具有边界检查。
- [ ] Flash 资源未覆盖系统保留区，Scatter 内存区域无重叠。
- [ ] 睡眠前后函数位置正确，外设恢复逻辑完整。
- [ ] 关键英文日志统一使用 `\r\n`，并包含模块、动作、结果或错误码。
- [ ] 未引入未知变量、函数、宏、库或外部符号。

## 常见问题处理

### 问题 1：需要修改框架结构

**处理方式：**

- 立即停止实施。
- 说明必须调整的原因。
- 对比原方案和新方案的优缺点。
- 等待用户明确批准后再修改。

### 问题 2：发现现有代码有 Bug

**处理方式：**

- 用大白话说明 Bug 的表现和可能原因。
- 提出最小修改的修复方案。
- 评估修复范围和潜在影响。
- 征求用户同意后再修复。

### 问题 3：不确定是否应新建函数或变量

**处理方式：**

- 先检查是否有可复用的现有资源。
- 评估新建的必要性。
- 确有必要时，说明原因并遵循文件组织规范。
- 不创建未使用、职责不清或无法验证的内容。

## 代码审查清单

提交代码前逐项检查：

- [ ] 是否保持原有框架结构和模块边界？
- [ ] 是否存在未定义、未初始化或未使用的变量、函数、宏、类型？
- [ ] 所有新增或修改函数是否具有完整中文注释？
- [ ] 新增或修改变量、宏是否具有中文说明？
- [ ] 是否按项目现有日志机制输出必要的英文日志？
- [ ] 是否使用了 `goto` 语句？
- [ ] 代码嵌套是否过深？
- [ ] `.c` 和 `.h` 文件内容是否分离正确？
- [ ] 是否遵循最小改动原则？
- [ ] 是否优先复用了现有资源？
- [ ] 是否改变了接口、时序、资源或调用关系？若改变，是否获得用户同意？
- [ ] 是否完成复核并输出修改总结报告？

## 示例场景

### 场景 1：添加新功能

用户：需要增加一个温度采集与显示功能。

**正确做法：**

1. 分析现有模块结构和数据流。
2. 找到合适位置接入采集、缓存和显示逻辑。
3. 复用已有数据获取函数和显示接口。
4. 在对应业务模块添加最小必要逻辑。
5. 添加中文注释和必要英文日志。
6. 复核后输出修改报告。

**错误做法：**

- 无必要修改底层驱动或重写整个模块。
- 创建大量重复函数而不复用已有接口。
- 不添加注释或日志。
- 不说明影响范围和复核结果。

### 场景 2：修复 Bug

用户：按键触发后没有反应。

**正确做法：**

1. 分析输入、事件传递和业务处理流程。
2. 定位实际失效环节。
3. 使用最小改动完成修复。
4. 说明修复原因并补充必要日志。
5. 复核是否引入新问题。

**错误做法：**

- 未定位问题就重写整个事件处理模块。
- 不说明修复原因和影响范围。
- 不检查变量、函数、状态和调用关系。

## 总结

本 skill 的核心要求是：

1. **保守改动**：保持原有框架稳定，最小化修改范围。
2. **优先复用**：优先使用已有变量、函数、接口和机制。
3. **注释与日志清晰**：新增或修改代码提供中文注释，并按需使用英文日志。
4. **沟通明确**：需求不清、存在矛盾或需要改框架时，必须先确认。
5. **质量可复核**：修改后检查变量、函数、调用关系、资源和时序，确保不引入未知问题。

遵循这些原则，可以使通用嵌入式固件项目保持稳定、清晰且易于维护。
