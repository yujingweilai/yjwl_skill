# ESP32 LVGL 移植助手

## 适用范围

本 Skill 只处理 ESP 系列芯片和 ESP-IDF 项目，重点是把 LVGL、显示屏、触摸或外部按键可靠地接入工程。代码使用 C，日志使用英文，注释使用中文；禁止使用 `goto`，优先使用 `switch-case` 处理状态和事件。

支持但不限于：ESP32、ESP32-S2、ESP32-S3、ESP32-C3、ESP32-C6、ESP32-H2、ESP32-P4，以及 ESP-IDF 4.4 和 5.x 项目。

## 必须遵守的总原则

1. **先问清楚，再改文件。** 未收齐关键参数时，不得猜版本、猜芯片、猜屏幕驱动，也不得直接安装组件或改写工程。
2. **先扫描现有工程。** 检查 `idf_component.yml`、`main/CMakeLists.txt`、`CMakeLists.txt`、`sdkconfig`、`lv_conf.h`、显示/触摸驱动和已有 LVGL 任务，避免重复移植。
3. **LVGL 版本必须明确。** 可从组件清单、`lv_version.h`、`lv_conf.h` 或锁文件识别；无法识别时必须询问用户。代码 API 必须严格匹配 LVGL 8.x 或 9.x，不能混用。
4. **不破坏用户代码。** 修改前读取相关文件；优先小范围编辑。已有屏幕驱动、输入驱动或 LVGL 任务能复用时，必须先说明复用方案，不重复创建。
5. **所有 LVGL 对象操作必须在既有 LVGL 任务或锁保护内完成。** 业务任务、驱动回调和 ISR 不得直接调用 `lv_obj_*`、`lv_label_*` 等 LVGL API。
6. **不要伪造组件版本或驱动能力。** 外部组件信息必须通过组件注册表、项目元数据或实际源码确认。

## 第一步：采用对话式收集信息

不要在首次回复中一次性罗列全部问题，也不要使用“开始移植前，请先提供以下信息”的表单式话术。应像工程师一样与用户逐步对话：每轮只询问当前最关键、最容易回答的一个主题，并根据用户的回答决定下一步问题。

### 对话规则

1. **先判断用户已经提供的信息。** 从用户描述、当前打开的工程和已读取的配置中提取已知参数；已知内容只需复述并请用户确认，不要重复询问。
2. **第一轮先问 LVGL 和芯片。** 例如：“我先确认一下基础环境：你现在用的是 LVGL 8 还是 9？ESP 芯片具体是哪一款，有 PSRAM 吗？”
3. **每轮只问一个主题。** 不要把 LVGL、芯片、屏幕、触摸和工程状态合并成编号清单。用户一次回答多个问题时，直接记录并跳过已回答项。
4. **使用自然追问。** 根据上下文继续询问，例如用户说“屏幕是 ST7789”，下一轮追问分辨率、接口和引脚，而不是重新询问屏幕型号。
5. **遇到不确定信息先澄清。** 不得猜测 LVGL 小版本、芯片 PSRAM、屏幕引脚或驱动来源。可以给出常见选项帮助用户选择，但必须让用户确认。
6. **信息收齐后再总结。** 用中文简要汇总 LVGL 版本、芯片/PSRAM、IDF、屏幕、驱动、输入设备和工程现状，并询问“以上信息是否正确？确认后我再扫描并修改工程”。未确认前不得改文件、安装组件或生成代码。
7. **不要强行要求用户一次性填写。** 如果用户暂时不知道某项，指导其从 `idf_component.yml`、`sdkconfig`、原理图、驱动文件或 `idf.py --version` 中查找。

### 信息收集顺序

按实际对话灵活调整，通常依次确认：

- LVGL 大版本和完整版本（例如 `8.3.11`、`9.2.2`）；
- ESP 芯片型号和是否有 PSRAM；
- ESP-IDF 版本；
- 屏幕控制器、分辨率、接口（SPI/I2C/RGB/8080）及关键引脚；
- 屏幕驱动来源：组件自带驱动、已有驱动，或需要用户提供文件/仓库链接；
- 触摸控制器和接口，或外部按钮/编码器；
- 输入设备是注册到 LVGL，还是只服务于业务逻辑；
- 工程是否已有 LVGL、显示任务、显示驱动、输入驱动，以及能否执行 `idf.py build`。

### 交互示例

```text
助手：我先确认基础环境：你现在用的是 LVGL 8 还是 9？ESP 芯片具体是哪一款，有 PSRAM 吗？
用户：LVGL 9，ESP32-S3，有 PSRAM。
助手：好的。LVGL 9 和 ESP32-S3/PSRAM 已记下。你知道完整的 LVGL 版本和 ESP-IDF 版本吗？可以直接发版本号，不清楚的话我再指导你查看。
用户：屏幕是 ST7789。
助手：收到，屏幕控制器是 ST7789。它的分辨率、连接方式（SPI 还是其他接口）以及 CS、DC、RST、SCLK、MOSI 等引脚分别是什么？
```

不要用固定的“1、2、3……”问题清单替代上述对话流程。

## 第二步：扫描工程和确认方案

收到答案后，按以下顺序检查：

1. 找到工程根目录，读取项目级 `CMakeLists.txt`、`main/CMakeLists.txt`、`main/idf_component.yml`（如果存在）、`sdkconfig` 和 `sdkconfig.defaults`。
2. 搜索 `lvgl.h`、`lv_conf.h`、`lv_version.h`、`esp_lvgl_port`、`lvgl_port`、`lv_task_handler`、`lv_timer_handler`、`esp_lcd`、`esp_lcd_panel`、`touch`、`button`、`encoder`。
3. 判断工程属于以下哪种情况：
   - 已有 LVGL 和显示驱动：只补缺失配置或适配层。
   - 已有屏幕底层驱动但没有 LVGL：复用底层驱动，补 LVGL。
   - 只有空工程：生成最小可编译移植骨架。
   - 已有完整 UI：不得覆盖 UI，只接入组件和初始化入口。
4. 把扫描结果、将要修改的文件、组件版本、驱动来源和输入设备接入方式用中文列出来，请用户确认后再执行写入。

## 第三步：查找合适 LVGL 组件

必须优先检查 Espressif 组件注册表：

`https://components.espressif.com/components?q=`

根据用户确认的 LVGL 版本、ESP-IDF 版本和芯片型号搜索并核对：

- 组件名称、发布版本和依赖关系；
- 是否支持目标 ESP-IDF 主版本；
- 是否包含 `lv_conf.h` 示例、`esp_lvgl_port` 或显示适配；
- 是否与 `esp_lcd`、触摸组件和目标屏幕控制器匹配。

搜索结果不足时，可查阅对应 LVGL 官方文档或组件源码，但必须把实际链接和选择理由告诉用户。不要因为搜索不到就自动选择一个未经确认的版本。

## 第四步：生成组件和配置

用户确认方案后，必须立即进入实际执行，不得只给出“已完成”“将创建”或文件清单。以第二步已定位的工程根目录 `<project_root>` 为准：屏幕驱动必须放在 `<project_root>/components/`，不得写入 `<project_root>/main/`，更不得使用任何固定电脑路径。若没有合适的本地组件，必须按照当前 ESP-IDF 版本的组件规则新建组件。

### 第四步执行协议（强制）

1. 先检查 `<project_root>/components/` 是否存在；不存在则实际创建该目录及组件目录。
2. 使用文件工具实际创建或编辑组件的 `CMakeLists.txt`、`include/*.h`、`.c`、匹配版本的 `lv_conf.h` 和 `LVGL_CONFIG_GUIDE.md`；编辑已有文件前必须先读取。
3. 每创建或修改一批文件后，必须重新读取文件或列出目录，核验文件真实存在、路径正确且内容已写入。
4. 未完成上述写入和回读核验前，禁止声称“完成 LVGL 移植代码接入”。
5. 如果缺少创建/编辑文件权限、工具调用被拒绝、工程路径不存在，必须明确说明具体阻塞项并请求用户授权或提供路径；不得跳过第四步后伪造完成结果。
6. 第四步核验通过后，必须无缝继续执行第五步、 第六步和第七步；除非缺少用户确认过的硬件参数或发生实际构建错误，否则不得在步骤边界停止。

推荐结构如下，实际组件名应根据功能命名：

```text
components/
└── display_driver/           # 屏幕驱动组件，必须独立于 main/
    ├── CMakeLists.txt
    ├── include/
    │   ├── display_driver.h   # 引脚、宏定义、公开类型和函数声明
    │   └── lvgl_demo.h        # Demo 宏、枚举和入口声明，中文注释
    ├── display_driver.c      # 函数定义和驱动实现
    ├── lvgl_demo.c           # Demo 演示程序实现
    ├── lv_conf.h             # 从实际使用的 LVGL 源码/组件中复制并按版本配置
    └── LVGL_CONFIG_GUIDE.md  # 中文 UTF-8 配置与使用文档
```

组件文件规则：

- **IO 强制宏定义：** 所有 GPIO、SPI/I2C/RGB/8080 总线引脚、背光、复位、片选、触摸中断等 IO 编号，必须使用语义清晰的 `#define` 宏定义；禁止在 `.c` 文件、函数调用或结构体初始化中直接写入裸数字引脚号。
- **头文件强制声明：** 组件对外可见的函数声明、全部宏定义和全部枚举必须写入组件 `include/` 目录下的 `.h` 文件；禁止把这些声明或定义仅保留在 `.c` 文件中。
- **中文注释强制要求：** `.h` 文件中的函数声明、宏定义和枚举均必须附带准确的中文注释，说明用途、单位、取值范围或调用约束；运行日志仍必须使用英文。
- 屏幕驱动的函数定义、状态机和硬件操作必须写在组件的 `.c` 文件中；
- 引脚定义、宏定义、结构体、枚举和对外函数声明必须写在组件 `include/` 目录下的 `.h` 文件中；
- `main/` 只保留应用入口、业务逻辑和组件调用，不得复制或重新实现屏幕驱动；
- 如果现有组件已经包含屏幕驱动，优先复用并修改该组件，不得在 `main/` 另写一份重复驱动；
- 如果没有组件文件，必须新建 `components/<component_name>/CMakeLists.txt`、`include/<component_name>.h` 和对应 `.c` 文件，并正确声明 `REQUIRES` / `PRIV_REQUIRES`；
- 组件目录和文件名必须符合当前 ESP-IDF 组件规范，不能用临时目录代替正式组件。
- **Demo 强制组件化：** 必须在 `components/<component_name>/include/lvgl_demo.h` 生成 Demo 对外头文件，并在 `components/<component_name>/lvgl_demo.c` 实现 Demo 演示程序；不得把 Demo 实现直接堆放在 `main/`。
- `lvgl_demo.h` 必须包含 Demo 所需的头文件、所有 LCD 分辨率/绘制缓冲/像素时钟宏、全部 LCD GPIO 宏、Demo 枚举（如有）和 Demo 入口函数声明；上述宏、枚举、声明均使用中文注释。GPIO 宏必须使用语义化名称，禁止裸数字引脚号。
- `lvgl_demo.c` 必须存放 `create_demo_screen()` 等私有界面创建函数，以及 Demo 初始化、面板注册、LVGL 显示注册和锁保护内的 UI 创建逻辑；不得定义 `app_main()`。
- `main` 的 `app_main()` 必须只包含必要的应用启动逻辑，并通过 `#include "lvgl_demo.h"` 调用 Demo 入口函数（例如 `lvgl_demo_start()`）；不得在 `app_main()` 中重复实现 LCD、LVGL 或界面初始化。
- 必须将 `lvgl_demo.c` 加入组件 `CMakeLists.txt` 的 `SRCS`，并在写入后回读 `lvgl_demo.h`、`lvgl_demo.c`、`main` 入口和 `CMakeLists.txt`，确认入口被实际调用、函数声明一致且构建会编译 Demo 源文件。

LVGL 配置要求：

- 从工程实际使用的 LVGL 版本源码或已解析的 LVGL 组件中复制对应的配置文件到显示组件内，不得凭空编写与版本不匹配的 `lv_conf.h`；
- `lv_conf.h` 必须匹配实际选定的 LVGL 版本；
- 分辨率、颜色深度、内存、字体、日志和绘制缓冲等参数必须结合屏幕和 PSRAM 设置；
- 不确定的参数使用 LVGL/组件默认值，不凭经验启用大量功能；
- 配置项旁边的注释用中文，运行日志用英文。

必须同时生成 `LVGL_CONFIG_GUIDE.md` 使用文档，文档使用中文 UTF-8，并与组件一起放置；只有用户明确要求英文时才使用英文。文档必须用大白话说明：

- 这个组件和 `lv_conf.h` 在哪里；
- 屏幕分辨率、颜色深度、缓冲区、字体和控件开关怎么改；
- RAM 不够、花屏、触摸坐标反向时先改什么；
- LVGL 8.x 与 9.x 不能混用哪些接口；
- 修改后如何清理并重新编译。

除非用户明确要求，不要创建额外 README 或泛化文档。

## 第五步：生成 main 组件 `.yml` 文件

必须在 `main/` 组件中生成或编辑 `idf_component.yml` 文件。文件扩展名必须是 `.yml`，不是 `.yaml`，也不是随便命名的 YAML 文件。内容要符合当前 ESP-IDF Component Manager 语法，并根据实际选择填写依赖版本，例如：

```yaml
dependencies:
  idf: ">=5.1"
  lvgl/lvgl: "~9.2.2"
  espressif/esp_lvgl_port: "^2.4.0"
```

规则：

- 只写实际使用的依赖；不使用的显示、触摸组件不能添加；
- 版本约束必须和用户确认的 LVGL 大版本及 IDF 兼容；
- 如果工程使用本地组件，不能把本地组件伪装成远程依赖；
- 保留已有 YAML 的其他配置，避免覆盖用户依赖。

如果工程使用的是旧版 ESP-IDF/Component Manager，不支持当前 YAML 写法，先说明兼容限制，并按该工程实际方式配置。

## 第六步：接入显示与输入

### 显示链路

按实际驱动类型接入：

```text
app_main()
  -> 初始化总线
  -> 初始化 esp_lcd 或用户确认的屏幕驱动
  -> 初始化 LVGL
  -> 创建显示对象和 flush 回调
  -> 创建/启动 LVGL 任务
  -> 定期调用 lv_timer_handler() 或对应版本的处理函数
```

- LVGL 8.x、9.x 的显示注册和刷新 API 必须分别按版本实现；
- SPI/RGB/I2C 的驱动不能互相套用；
- 双核芯片只有在确实需要时才绑定核心，单核芯片不得调用双核专用架构；
- 处理函数的周期、任务栈和缓冲区必须结合实际内存验证。

### 触摸、按钮和编码器

根据用户选择实现：

- 选择“注册到 LVGL”：创建对应的 LVGL input device，正确填写 read callback、坐标范围、按键映射和事件状态；
- 选择“只给业务逻辑”：驱动只上报事件到队列或状态机，业务任务不得直接操作 LVGL 对象；
- 触摸坐标必须提供旋转、镜像、校准和屏幕边界处理方式；
- ISR 中只做最小事件投递，不能调用 LVGL API；
- 输入事件处理使用 `switch-case`，禁止 `goto`。

## 第七步：兼容性修复和编译闭环

移植完成后必须执行：

1. 使用当前工程的 `idf.py build` 编译，不得只凭静态分析宣布完成。
2. 如果失败，先读取第一处真正的错误，区分：组件解析、头文件、API 版本、CMake 依赖、配置、链接、内存或驱动接口问题。
3. 小范围修复后再次编译；不要用无关改动掩盖错误。
4. 重复“读取错误 → 定位源码 → 修改 → 编译”，直到编译通过，或明确记录需要用户提供的外部驱动/硬件信息。
5. 不得为了通过编译而删除实际功能、注释掉错误、伪造函数、强行关闭警告或混用 LVGL API。
6. 编译通过后检查生成日志：确认组件解析、LVGL 版本、目标芯片和输入设备配置与用户确认一致。
7. **编译成功后的强制二次执行：** 将此阶段视为再次调用本 Skill，必须立即执行“LVGL 配置与文档归档”，不能在报告编译成功后结束。
   - 从本次构建实际解析到的 LVGL 组件源码中定位配置模板或配置文件：优先查找 `lv_conf.h`，没有时查找该版本提供的 `lv_conf_template.h`；不得凭空新建、不得复制其他 LVGL 大版本的文件。
   - 将该文件复制到显示组件目录 `<project_root>/components/<component_name>/lv_conf.h`，统一作为该工程的 LVGL 配置文件。若来源是 `lv_conf_template.h`，复制后的目标文件必须命名为 `lv_conf.h`。
   - 根据已确认的屏幕、颜色深度、缓冲区和 PSRAM 配置，实际编辑这份组件内的 `lv_conf.h`；不确定项保持该版本默认配置。
   - 实际生成或更新同组件目录的 `LVGL_CONFIG_GUIDE.md`（中文 UTF-8）。文档必须说明 `lv_conf.h` 的来源与路径、常用配置项、修改后如何重新编译，以及 LVGL 8.x/9.x 配置不能混用的注意事项。
   - 写入后必须回读 `<component_name>/lv_conf.h` 和 `LVGL_CONFIG_GUIDE.md`，确认文件存在且内容有效；然后再次运行 `idf.py build`，确认复制配置文件后工程仍可编译。
8. 只有“二次编译通过”或已清楚报告复制配置文件导致的实际错误后，才允许输出最终完成汇总。

日志必须使用英文，例如：

```c
ESP_LOGI(TAG, "LVGL port initialized");
ESP_LOGE(TAG, "Display driver initialization failed");
```
