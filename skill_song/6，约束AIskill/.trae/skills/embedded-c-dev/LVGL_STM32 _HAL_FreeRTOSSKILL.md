# 嵌入式C开发规范

本skill用于指导LVGL + STM32 HAL + FreeRTOS固件项目的代码开发，确保代码质量、框架一致性和可维护性。

## 核心原则

### 1. 保持原有框架结构
**绝对禁止**改变以下层次结构：
- LVGL组件层（UI界面层）
- 用户调用层（业务逻辑层）
- HAL库层（硬件抽象层）
- STM32框架层（底层驱动）
- FreeRTOS状态机（任务调度）
- 用户自定义状态机框架（业务状态管理）

任何新增代码必须符合现有代码框架风格。如果必须改动框架结构，需要：
1. 先询问用户是否同意
2. 详细说明为什么要这样改
3. 对比新旧方案的优劣势
4. 获得用户明确批准后才能执行

### 2. 用户自定义状态机框架规范

用户直接创建的状态机框架必须遵循以下规范：

#### 2.1 状态机结构定义
```c
/* 状态机结构体，放在.h文件中 */
typedef struct {
    uint8_t current_state;    // 当前状态
    uint8_t previous_state;   // 上一个状态
    uint8_t event;            // 触发事件
    bool state_changed;       // 状态是否改变标志
} StateMachine_t;
```

#### 2.2 状态枚举定义
```c
/* 状态枚举，放在.h文件中 */
typedef enum {
    STATE_IDLE = 0,      // 空闲状态
    STATE_RUNNING,       // 运行状态
    STATE_ERROR,         // 错误状态
    STATE_MAX            // 状态最大值，用于边界检查
} State_t;
```

#### 2.3 事件枚举定义
```c
/* 事件枚举，放在.h文件中 */
typedef enum {
    EVENT_NONE = 0,      // 无事件
    EVENT_START,         // 启动事件
    EVENT_STOP,          // 停止事件
    EVENT_RESET,         // 复位事件
    EVENT_MAX            // 事件最大值，用于边界检查
} Event_t;
```

#### 2.4 状态机处理函数
```c
/**
 * @brief 状态机处理函数，放在.c文件中
 * @param sm 状态机结构体指针
 * @return 0:成功 其他:错误码
 * @note 在FreeRTOS任务中周期调用
 */
int state_machine_process(StateMachine_t *sm)
{
    if (sm == NULL) {
        return -1;  // 参数错误
    }
    
    sm->state_changed = false;
    
    switch (sm->current_state) {
        case STATE_IDLE:
            // 空闲状态处理
            if (sm->event == EVENT_START) {
                sm->previous_state = sm->current_state;
                sm->current_state = STATE_RUNNING;
                sm->state_changed = true;
            }
            break;
            
        case STATE_RUNNING:
            // 运行状态处理
            if (sm->event == EVENT_STOP) {
                sm->previous_state = sm->current_state;
                sm->current_state = STATE_IDLE;
                sm->state_changed = true;
            } else if (sm->event == EVENT_RESET) {
                sm->previous_state = sm->current_state;
                sm->current_state = STATE_IDLE;
                sm->state_changed = true;
            }
            break;
            
        case STATE_ERROR:
            // 错误状态处理
            if (sm->event == EVENT_RESET) {
                sm->previous_state = sm->current_state;
                sm->current_state = STATE_IDLE;
                sm->state_changed = true;
            }
            break;
            
        default:
            // 未知状态，恢复到空闲
            sm->current_state = STATE_IDLE;
            sm->state_changed = true;
            break;
    }
    
    // 清除事件
    sm->event = EVENT_NONE;
    
    return 0;
}
```

#### 2.5 状态机框架约束
- **禁止改变状态机框架结构**：状态机结构体、状态枚举、事件枚举的定义方式必须保持一致
- **状态转换必须清晰**：每个状态转换都要有明确的事件触发
- **状态处理函数必须完整**：每个状态都要在switch-case中处理
- **必须有默认处理**：switch语句必须有default分支
- **状态机变量必须初始化**：在系统启动时初始化状态机结构体
- **事件清除机制**：处理完事件后必须清除事件标志
- **强制文件组织规范**：所有生成的宏定义、结构体、枚举类型、函数声明均需要放入对应文件的.h文件中，实现部分放在.c文件中

#### 2.6 状态机使用示例
```c
// 全局状态机变量，放在.c文件中
StateMachine_t g_motor_sm;

/**
 * @brief 初始化电机状态机
 * @param 无
 * @return 无
 */
void motor_state_machine_init(void)
{
    g_motor_sm.current_state = STATE_IDLE;
    g_motor_sm.previous_state = STATE_IDLE;
    g_motor_sm.event = EVENT_NONE;
    g_motor_sm.state_changed = false;
}

/**
 * @brief 发送事件到状态机
 * @param event 事件类型
 * @return 无
 */
void motor_send_event(Event_t event)
{
    g_motor_sm.event = event;
}

/**
 * @brief 电机任务，在FreeRTOS中周期调用
 * @param pvParameters 任务参数
 * @return 无
 */
void motor_task(void *pvParameters)
{
    motor_state_machine_init();
    
    while (1) {
        state_machine_process(&g_motor_sm);
        
        if (g_motor_sm.state_changed) {
            // 状态改变后的处理
            switch (g_motor_sm.current_state) {
                case STATE_RUNNING:
                    // 启动电机
                    break;
                case STATE_IDLE:
                    // 停止电机
                    break;
                default:
                    break;
            }
        }
        
        vTaskDelay(10);  // 10ms周期
    }
}
```

### 3. 禁止幽灵变量
- 所有声明的变量必须被使用
- 所有使用的变量必须有明确定义
- 禁止出现未定义或未使用的变量

### 4. 详细中文注释要求
每个代码元素必须包含详细中文注释：

**函数注释示例：**
```c
/**
 * @brief 函数功能说明
 * @param paramName 参数含义说明
 * @param anotherParam 另一个参数说明
 * @return 返回值含义说明
 * @note 其他注意事项
 */
```

**变量注释示例：**
```c
int counter = 0;  // 计数器，用于记录xxx的次数
```

**宏定义注释示例：**
```c
#define MAX_BUFFER_SIZE 1024  // 最大缓冲区大小，单位：字节
```

### 5. 代码风格规范

#### 5.1 禁止goto语句
- 使用结构化控制流（if-else、switch-case、循环）
- 通过函数封装和返回值处理复杂逻辑

#### 5.2 减少嵌套层数
- 嵌套深度尽量控制在3~6层以内
- 优先使用早返回（early return）模式
- 能用分支判断就不用深层嵌套

**错误示例：**
```c
if (condition1) {
    if (condition2) {
        if (condition3) {
            // 深层嵌套
        }
    }
}
```

**正确示例：**
```c
if (!condition1) return;
if (!condition2) return;
if (!condition3) return;
// 扁平化逻辑
```

#### 5.3 文件组织规范

**`.c` 文件内容：**
- 函数实现
- 静态变量（文件作用域变量）
- 局部变量定义

**`.h` 文件内容：**
- 宏定义（#define）
- 函数声明（extern声明）
- 类型定义（typedef、struct、enum）
- 配置常量
- 头文件保护符（#ifndef、#define、#endif）

### 6. 最小改动原则

#### 6.1 优先复用现有资源
- 优先使用已有的变量
- 优先调用已有的函数
- 优先在原函数内修改，而不是新建函数
- 避免过度封装和不必要的抽象

#### 6.2 改动评估标准
在修改代码前，评估：
1. 是否必须改动？
2. 能否在现有代码基础上修改？
3. 改动范围是否最小化？
4. 是否引入了不必要的复杂性？

#### 6.3 LVGL局部更新强制要求
- **强制要求**：高亮与非高亮之间的移动、切换、选中状态变化，以及其他未特别强调刷新方式的界面变化，默认必须采用局部更新。
- 只更新状态发生变化的控件、对象或受影响区域，不得重绘无关控件或无关区域。
- **禁止默认执行全部重绘或整屏重绘**，包括但不限于重新创建整个页面、刷新全部控件、使整个屏幕区域失效。
- 仅当用户明确要求全部重绘或整屏重绘，或者局部更新客观上无法实现且已向用户说明原因并获得明确同意后，才允许执行全部重绘或整屏重绘。
- 实现高亮移动时，应分别局部恢复旧高亮对象并局部更新新高亮对象，优先复用现有控件和刷新函数。
- 修改完成后必须复核实际刷新范围，确认没有因父容器刷新、页面重建或大范围失效而变相触发全部重绘或整屏重绘。

#### 6.4 新增页面对象化与生命周期强制要求
- **强制要求**：新增页面必须创建对应的 LVGL 页面对象及其必要的子对象，不得仅使用零散全局变量或脱离 LVGL 对象体系实现页面。
- 页面对象必须具有清晰的创建、访问或更新、删除生命周期；外部模块可通过对外声明的页面接口调用页面功能、修改对象内部数据以及请求删除页面。
- 外部模块不得绕过页面接口随意操作页面内部私有对象；需要被外部操作的能力应复用现有接口，或以最小改动增加明确的创建、更新和删除接口。
- 页面内部数据发生变化时，只更新对应的 LVGL 对象或受影响区域，并继续遵守“局部更新优先、禁止默认整屏重绘”的强制要求。
- 创建父子对象、设置样式、注册事件、更新内容和删除对象，必须符合项目当前使用的 LVGL 版本及原有 UI 框架，不得混用不同 LVGL 版本的 API。
- LVGL 对象的创建、更新和删除必须在 LVGL 允许的线程上下文中执行；FreeRTOS 其他任务不得在缺少项目既有 LVGL 互斥或消息机制时直接操作 UI 对象。
- 删除页面时必须使用符合当前 LVGL 版本的对象删除机制，并同步清理或置空外部保存的对象引用，禁止继续访问已删除对象，避免重复删除、悬空指针和内存泄漏。
- 修改完成后必须复核页面对象是否成功创建、外部接口是否可用、内部数据是否正确更新、删除流程是否安全，以及 UI 层级、事件和样式是否符合原有设计。

#### 6.5 使用 Figma 链接时的 LVGL 坐标层级规则
- **触发条件**：仅当用户明确提供或要求使用 Figma 链接获取界面数据、坐标或布局时，才应用本节规则；未使用 Figma 链接时禁止触发本节规则。
- 坐标层级统一采用“屏幕 → 父 → 子 → 子子”的方式。
- 第一层元素容器的坐标相对于屏幕原点 `(0, 0)`。
- 第一层元素容器内部的容器或元素，其坐标相对于第一层元素容器。
- 第三层及更深层元素的坐标相对于各自的直接父容器，不得直接使用相对于屏幕的绝对坐标。
- Figma 返回屏幕绝对坐标时，子元素相对坐标按 `子元素相对坐标 = 子元素屏幕绝对坐标 - 直接父容器屏幕绝对坐标` 转换后，再传入 LVGL 的位置设置接口。
- 设置 LVGL 对象坐标前，必须确认对象的直接父对象，并检查父容器的内边距、边框和滚动偏移，避免实际显示位置偏移。

### 7. 分析与复核流程

#### 7.1 修改前分析
用大白话说明：
- 当前代码的问题是什么
- 为什么要这样修改
- 修改的预期效果

#### 7.2 修改后复核
检查以下内容：
- 程序固件是否存在异常错误
- 变量使用是否正确
- 函数调用是否匹配
- 内存分配是否合理
- 中断和任务调度是否受影响

#### 7.3 修改总结报告
修改完成后，必须用大白话说明：
1. **改了哪个文件**：列出所有修改的文件路径
2. **为什么这样改**：每个文件的修改原因
3. **改动位置**：具体到函数名、行号范围
4. **影响范围**：修改可能影响的其他模块

**报告示例：**
```
修改总结：
1. 文件：src/ui/main_page.c
   原因：修复按钮点击无响应问题
   位置：button_click_callback函数，第45-60行
   改动：添加了事件处理逻辑，修复了状态判断条件
   
2. 文件：include/config.h
   原因：调整缓冲区大小以适配新需求
   位置：第23行，BUFFER_SIZE宏定义
   改动：将BUFFER_SIZE从512改为1024
```

### 8. 提示词优化与确认机制

#### 8.1 自动优化提示词格式（父类-子类-子类结构）
收到用户的提示词后，先自动将其整理为层级结构，确保需求清晰、有条理：

**优化规则：**
- **第一层（父类）**：识别用户的最终目标或大方向（如"修改UI界面"、"修复通信bug"）
- **第二层（子类）**：拆解实现目标所需的具体模块或步骤（如"修改温度显示组件"、"调整串口发送逻辑"）
- **第三层（子类）**：进一步细化每个模块的具体操作点（如"修改lv_label文本刷新频率"、"调整UART DMA缓冲区大小"）

**优化输出格式示例：**
```
提示词优化结果：
├── 父类：修改UI界面显示
│   ├── 子类：温度显示模块
│   │   ├── 子类：修改lv_label刷新频率为500ms
│   │   └── 子类：添加温度单位切换按钮
│   └── 子类：状态栏显示
│       └── 子类：添加WiFi信号强度图标
```

**处理方式：**
1. 收到用户提示词后，自动分析并整理为层级结构
2. 将优化后的结构展示给用户，让用户确认理解是否正确
3. 如果用户确认无误，再进入后续开发流程

#### 8.2 提示词错误检测与确认机制
在分析用户提示词时，如果发现以下问题，必须暂停并用大白话向用户解释确认：

**需要确认的情况：**
- **错别字**：如用户写"温渡显示"，应指出"你说的'温渡'是不是'温度'？"
- **意思不清楚**：如用户写"改一下那个东西"，应指出"你说的'那个东西'具体是指哪个功能或模块？"
- **专业术语可能有误**：如用户写"DMA中端"，应指出"你说的'DMA中端'是不是'DMA中断'？"
- **逻辑矛盾**：如用户要求"不改动框架但要重写整个模块"，应指出矛盾之处
- **信息缺失**：如缺少关键参数、文件路径、功能描述等

**确认流程：**
1. 发现提示词有问题时，**立即暂停**，不要继续往下做
2. 用大白话把问题解释清楚，说明哪里可能有误
3. 给出你的猜测或建议（如果有的话）
4. **等待用户确认或补充信息**，用户回复后才能继续
5. 如果用户补充后仍有疑问，继续追问直到完全明确

**确认示例：**
```
⚠️ 提示词确认：
你提到要修改"串口的波特律"，我猜你可能是想说"串口的波特率"？
另外你说"改快一点"，是指把波特率调高吗？目前波特率是9600，你想调到多少？
请确认后我再继续。
```

## 工作流程

当用户请求修改嵌入式C代码时，按以下步骤执行：

1. **提示词优化**：将用户的提示词整理为"父类-子类-子类"层级结构，展示给用户确认
2. **提示词检查**：检查提示词是否有错别字、意思不清、信息缺失等问题，有问题则用大白话向用户确认，等待用户确认或补充后才能继续
3. **理解需求**：明确用户要解决的问题
4. **分析现状**：阅读相关代码，理解现有框架
5. **制定方案**：基于最小改动原则设计方案
6. **评估影响**：检查是否需要改动框架结构
7. **征求同意**：如需改动框架，先询问用户
8. **实施修改**：按照规范编写代码
9. **添加注释**：为所有新增代码添加详细中文注释
10. **复核检查**：检查代码是否存在异常
11. **输出报告**：用大白话总结修改内容

## 常见问题处理

### 问题1：需要修改框架结构
**处理方式：**
- 立即停止修改
- 向用户说明为什么需要改动框架
- 对比新旧方案的优劣势
- 等待用户批准后再执行

### 问题2：发现现有代码有bug
**处理方式：**
- 用大白话说明bug的表现和原因
- 提出修复方案
- 评估修复范围
- 征求用户同意后修复

### 问题3：不确定是否应该新建函数/变量
**处理方式：**
- 检查是否有可复用的现有资源
- 评估新建的必要性
- 如果必须新建，说明原因
- 遵循文件组织规范

## 示例场景

### 场景1：添加新功能
用户：需要添加一个温度显示功能

**正确做法：**
1. 分析现有UI框架结构
2. 找到合适的位置添加LVGL组件
3. 复用现有的数据获取函数
4. 在用户调用层添加逻辑
5. 添加详细注释
6. 输出修改报告

**错误做法：**
- 直接修改HAL层代码
- 创建大量新函数而不复用现有资源
- 不添加注释
- 不输出修改报告

### 场景2：修复bug
用户：按钮点击没反应

**正确做法：**
1. 分析事件处理流程
2. 定位问题所在
3. 用最小改动修复
4. 详细说明修复原因
5. 复核是否引入新问题

**错误做法：**
- 重写整个事件处理模块
- 不说明修复原因
- 不检查影响范围

## 总结

本skill的核心是：
1. **保守改动**：保持框架稳定，最小化修改
2. **详细注释**：所有代码元素都要有中文注释
3. **清晰沟通**：用大白话说明问题和解决方案
4. **质量保证**：修改后必须复核，确保无异常

遵循这些原则，可以确保嵌入式固件项目的可维护性和稳定性。
